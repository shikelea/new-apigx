# APIGX 中转分享与工具中心规划

## 本轮落地边界

- 中转分享先作为公共资料页，支持作者、Markdown、更新时间和状态说明；首版不做排行榜、不做综合评分、不替用户保管上游 Key。
- 工具页先展示能力边界，避免在没有受控后端测试接口时伪造测速或“掺水检测”结果。
- 分享渠道连通性测试复用 New API 的渠道测试控制器；APIGX 只负责 owner 校验、渠道归属和模型白名单。

## 工具接入候选
## 已核实的开源候选

- `mintesnot-teshome/llm-verify`：MIT 许可证，Python/FastAPI 独立服务。支持 OpenAI 兼容和 Anthropic 风格端点，提供基准跑、结果、行为指纹与深度分析接口；需要测试服务的访问令牌以及待测/基线渠道的 Key。它的结论明确是概率性信号，`NO_FRAUD_SIGNALS` 也不等于“已验证真实”。适合隔离部署后由 APIGX 服务端受控调用，不能把 Key 放到浏览器，也不应把“欺诈”直接作为封禁依据。
- `hanlinwenyuan/hlwy-ai-checker`：LGPL-2.1，Python + HTML 本地工具，使用官方模型标定结果与第三方渠道的统计指纹做比较；README 明确提示结果受随机性、模型版本、采样参数、网络波动和样本数影响，不能作为商业纠纷的绝对事实依据。适合参考测试流程和解释文案；若正式集成，需要遵守 LGPL 条款并优先以独立服务或可替换适配器接入。
- 两个项目都不是 APIGX 的渠道适配器，不能替换 New API 的 `TestChannel`。分享渠道连通性继续走基座实现；外部项目只用于受控质量检查/指纹任务。


- `idemerge/llm-api-bench`：参考自托管、多供应商/兼容 OpenAI 端点的测试任务、并发、健康状态和历史结果模型。
- `saksham10arora-dotcom/llm-bench`：参考 TTFT、总延迟、流间隔、吞吐、成本和 p50/p95/p99，并区分冷/热请求。
- `Jwrede/llm-bench-data`：参考按小时采样的延迟、TTFT 和吞吐时间序列结构。
- New API 自带渠道测试：作为 APIGX 渠道详情的默认连通性测试实现，不另写适配器。

这些项目只作为指标和任务模型参考，正式接入前需要单独检查许可证、凭据处理和是否适合生产环境。测速应由服务端受控发起，记录首字节、首 Token、完整响应、输出 Token 数、错误分类和采样时间；冷启动与热启动要分开。

## “掺水”检测边界

不把“检测 AI 文本”做成真假判定。可实现的第一阶段是可解释质量信号：空响应、重复片段、异常短响应、流式中断、声明 Token 与实际文本明显不一致、同一请求多次结果差异过大。学术检测器在跨模型、跨语言和改写场景下仍有明显不确定性，不能直接作为封禁或排名依据。

## 后续设计顺序

1. 增加服务端受控测速任务和一次性凭据引用，禁止把明文 Key 持久化到浏览器或结果表。
2. 复用底座 endpoint/adaptor 和 APIGX 质量事件，统一 TTFT、吞吐、总延迟、HTTP 状态和错误分类。
3. 增加结果的有效期、样本数和“样本不足”状态；中转分享只展示最近验证状态，不生成综合排名。
4. 再考虑批量比较、历史趋势和质量信号详情；任何质量信号均需保留原始证据与采样上下文。
5. 通过管理员设置控制工具是否公开，默认关闭需要凭据的测试入口。
