# 阶段 0 验收报告（T0.9）

对象：底座固定提交 `69a50029819a26c53e6babd276d49cfe2f8880ad` + 可控上游替身。
环境：底座 `127.0.0.1:3000`（PostgreSQL 5433 + Redis 6379）、替身 `127.0.0.1:8100`。
脚本：`tools/stage0-verify/wire-base.mjs`、`chat-probe.mjs`、`acceptance.mjs`（可重复执行）。

> **验证性质**：全部为**本地替身实验**，没有任何真实上游参与，不产生费用。
> 替身通过**不等于**真实上游兼容——真实适配器联调属阶段 3。
> 结论分三档：`PASS`（底座已具备）｜`GAP`（底座缺失，需我们在扩展点补齐）｜`FAIL`（实验本身失败）。

## 0. 结论速览（对应计划书 §11 阶段 0 的 5 项验收）

| 验收项 | 结论 | 依据 |
|---|---|---|
| ① 归属隔离 | 用户/令牌面 **PASS**；渠道归属 **GAP** | A1 |
| ② 定向渠道 / Key 不被二次抽选 | **PASS** | A2 |
| ③ 无余额但正成本估算 | 正成本估算 **PASS**；无余额被拒 → **GAP** | A3 |
| ④ 预算与并发准入 | 预算准入 **PASS**；渠道级并发上限 **GAP** | A4 |
| ⑤ 任务 / 文件对象隔离 | 路由鉴权 **PASS**；端到端归属取证**未完成** | A5 |

## 1. A1 两账号归属隔离

两个账号：`apigxroot`(id=1, role=100)、`apigxuserb`(id=2, role=1)。

| 观测 | 结果 |
|---|---|
| B 的令牌列表是否看到 root 的令牌 | 看不到（0 条）→ **PASS** |
| B 访问渠道管理面 `/api/channel/` | HTTP 403 `insufficient privileges` → **PASS** |
| B 访问用户管理面 `/api/user/` | HTTP 403 → **PASS** |
| B 读取他人令牌明文 `POST /api/token/1/key` | `record not found` → **PASS** |
| 渠道归属 | 底座 `channels` 表**没有 owner 字段**（`model/channel.go:23-60`）→ **GAP** |

**结论**：底座的「用户 / 令牌」两层隔离是现成的、可靠的；但**渠道是全局资源**，没有分享者归属概念。计划书 §5.2 要求的「受 owner 约束的分享者接口」必须由我们新增（对应扩展点 E2、TD-08）。

## 2. A2 定向渠道 + 三把 Key 不被二次抽选（最关键的一项）

造了两个渠道服务**同一个模型**：

| 渠道 | id | 上游 Key |
|---|---|---|
| `stub-pin-a` | 2 | `sk-stub-PIN-A1`、`sk-stub-PIN-A2`（模式 `multi_to_single`，池策略 `polling`） |
| `stub-pin-b` | 3 | `sk-stub-PIN-B1` |

**实验一：不指定渠道（自动选路）** —— 6 次请求全部 200；替身看到的 Key 指纹分布：
`PIN-A1 ×3、PIN-A2 ×2、PIN-B1 ×1`
→ 跨渠道随机选路生效，渠道内 Key 池**实际轮换**（A1/A2 交替）。

**实验二：定向到渠道 A**（令牌明文 + `-2`）—— 6 次请求全部 200；替身收到的 Key：
`PIN-A2 ×3、PIN-A1 ×3`，**渠道 B 的 Key 一次都没有出现**。

→ **PASS**：底座现有的 `ChannelPin` 机制确实能把请求钉在指定渠道上，**不存在「已定渠道被转发器二次抽选」**；渠道内 Key 由分享者配置的池策略决定（正是计划书 §9.2「渠道选择与 Key 选择分别配置」的语义）。

**注意两点**：
1. pin 的语法是「令牌明文 + `-` + 渠道 ID」，且源码**只允许管理员**使用（`middleware/auth.go:536-551`，普通用户返回 403 `普通用户不支持指定渠道`）。我们的「指定分享来源」必须改为基于资源授权的判断，而不是删除这个管理员判断（TD-08）。
2. 新建渠道后底座的内存缓存需要约 60 秒才同步（实验里显式等待后再测）。

## 3. A3 无余额但正成本估算

用普通用户 B（非 root，避免特权干扰），模型 `stub/model-x-202609`。

**第一步：给额度，验证成本估算为正**

| 观测 | 数值 |
|---|---|
| 调用前额度 | 100000 |
| 调用后额度 | 98275 |
| **单次消耗** | **1725**（按 `QuotaPerUnit=500000` 折约 **＄0.00345**） |
| 到达上游 | 1 次 |

→ **PASS**：底座确实对**未在我们的价格库里配置过**的模型也产生了**正的估算成本**并记账（root 账号 `used_quota` 累计 75900→91425 亦印证）。

**第二步：把额度置 0，验证余额前置条件**

```
HTTP 403 {"code":"insufficient_user_quota",
          "message":"用户额度不足, 剩余额度: ＄0.000000"}
到达上游：0 次
```

→ **GAP**：底座存在**硬性充值余额前置**。计划书 §6 要求免费共享模式下「保持鉴权、额度与计量，取消用户充值余额前置条件」，因此 `usage_only` 必须在计费会话的**资金来源**维度做分支（见 `docs/stage0/metering-state.md` §2.3），**不能**用「把价格置 0」或「给超大余额」绕过。

## 4. A4 预算与并发准入

**并发**：让替身把每个请求握 1.5 秒，再并发发 8 个。

| 观测 | 结果 |
|---|---|
| 8 个请求的返回 | 全部 200 |
| 替身收到 | 8 个请求，**到达时间跨度仅 170ms**（远小于 1500ms） |
| 含义 | 8 个请求**同时在飞** → 底座**没有渠道 / Key 级并发上限** → **GAP** |

**预算**：把平台令牌额度设为 20000（单次约需 7.6k），再并发发 6 个。

| 观测 | 结果 |
|---|---|
| 6 个请求的返回 | `403,403,403,200,403,403` —— **恰好 1 个通过** |
| 到达上游 | **1 次**（被拒的 5 个根本没出站） |
| 令牌额度 | 20000 → **18275**（未被击穿，未出现负数） |
| 含义 | **PASS**：底座的 Redis Lua 原子预留（`model/quota_reserve.go:203-240`）确实做到「先预留、超额拒绝、不超支」，而不是「先发再记账」 |

**这两条合起来给出一个明确的施工图**：**额度类限制是现成可复用的**（原子预留 + 准入拒绝），**但并发/速率类共享容量控制必须我们新增**（计划书 §9.2 的 [N4j] 判断在本机得到实测支持）。

## 5. A5 任务 / 文件对象隔离

| 探测 | 无凭据 | 有凭据 | 判定 |
|---|---|---|---|
| `GET /v1/tasks/<不存在>` | 401 | 404 | PASS |
| `GET /v1/tasks/<不存在>/artifacts` | 401 | 404 | PASS |
| `GET /v1/tasks/<不存在>/artifacts/any/content` | 401 | 404 | PASS |

→ 路由层的「无凭据拒绝、不存在对象统一 404（不泄露存在性）」是**PASS**。
→ 但本轮**没有真实异步任务**，因此「A 的任务 B 读不到」这一端到端归属隔离**未取证**（需要真实可用的视频/图片上游，属阶段 3）。底座现有的产物访问是「令牌**或**签名能力」二选一（`middleware/task_artifact_access.go:174`），默认策略需要我们收紧为鉴权下载（扩展点 E9）。

## 6. 过程中确认的底座行为（踩坑记录，避免重复摸索）

| 行为 | 说明 |
|---|---|
| dashboard 鉴权只认 `Authorization` 头 | `middleware/auth.go:159`；**不看 cookie**。登录返回的 `data.access_token`（内部会话 JWT）才是凭证 |
| 建渠道必须给 `mode` | `controller/channel.go:652` `AddChannelRequest{Mode, Channel}`；单 Key 用 `"single"`，多 Key 用 `"multi_to_single"`（`:723`）自带换行拼接与 `MultiKeySize` |
| 令牌创建字段必须在**顶层** | `tokenRequest` 是**内嵌** `model.Token`（`controller/token.go:35-38`），包成 `{token:{...}}` 会静默建成**空名令牌** |
| 令牌明文要另取 | `POST /api/token/:id/key`（`controller/token.go:188-206`） |
| 改用户额度不能走 `PUT /api/user/` | 必须走 `POST /api/user/manage` + `{action:"add_quota", mode:"override", value}`（`controller/user.go:1043-1047`、`user_quota.go:14-47`） |
| 关键接口有频率限制 | `CriticalRateLimit`：默认 **20 次 / 20 分钟**（`common/constants.go:219-220`），作用于登录与取令牌明文等接口；被限流时返回 **429 且响应体为空** |
| 磁盘占用会拦请求 | `SystemPerformanceCheck` 默认阈值 95%（`middleware/performance.go:64-67`），本机 D 盘 98.9% 时返回 `503 system_disk_overloaded` |
| 渠道缓存约 60 秒同步 | 新建渠道后需等待，否则分发器报 `No available channel for model ... (distributor)` |

## 7. 未验证 / 已知限制

1. 全部为**替身实验**；未调用任何真实上游，因此不构成任何真实兼容性证明。
2. ⑤ 的端到端归属隔离未取证（无真实异步任务）。
3. 「正成本估算」用的是底座对未配置价格模型的默认口径，**没有**验证与上游真实账单的一致性（那需要真实凭据）。
4. 并发实验只验证了「没有并发上限」这一事实，**没有**做压测或性能评估。
5. 本机为 Windows 单机开发环境，容量结论不能外推到生产。
