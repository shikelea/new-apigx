# 阶段 0 闸门评审（T0.10）

依据：阶段 0 的全部产出（`docs/stage0/*.md`、`docs/architecture/*.md`）与实测验收报告 `docs/stage0/acceptance-report.md`。
目的：回答计划书 §11 阶段 0 的闸门问题——**免费计量、凭据选择、资源授权三条路径能否在既有扩展点闭合**；并给出阶段 1 的详细任务与单人排期重估。

> 本评审基于**源码阅读 + 本地替身实测**，没有真实上游参与。结论中的「可闭合」指**设计上可在既有扩展点实现**，不等于已实现。

## 1. 三条路径的判定

### 1.1 免费计量（`usage_only`）→ **可闭合**（改动集中在 1 个扩展点）

| 维度 | 判定 |
|---|---|
| 扩展点 | `service/billing_session.go:377-476`（`NewBillingSession` 的资金来源分支）+ `service/funding_source.go` 的 `FundingSource` 抽象 |
| 为什么可闭合 | 底座已经把「预留 → 结算 → 退款」与**资金来源**解耦，`WalletFunding` / `SubscriptionFunding` 是同级实现；新增一个「只记账不动钱包」的资金来源是**同一维度的扩展**，不需要另起计量 |
| 实测支持 | A3：零余额被 `403 insufficient_user_quota` 拦住（前置条件确实存在，且位于资金侧）；同一实验证明**正成本估算已成立**（单次扣 1725，约 ＄0.00345） |
| 必须绕开的两个陷阱 | ①**不得**走 `FreeModel` 短路（`relay/request_billing.go:61-64` 会直接 `return nil`、不建会话，导致既无结算也无计量 → TD-10）；②`TrustQuota` 旁路会连令牌额度预扣一起跳过（`service/billing_session.go:317-350` → TD-09），因此 APIGX 的容量预留必须**独立于** `effectiveQuota` |
| 风险 | 计费是全站核心链路，改动必须配回归测试（饱和钳制、负数防护、幂等退款） |

### 1.2 凭据选择（多 Key / 定向来源）→ **可闭合**（但扩展点本身风险最高）

| 维度 | 判定 |
|---|---|
| 扩展点 | 渠道侧：`service/channel_select.go:15 GetChannelConstraints` + `dto.ChannelPin`（pin 机制）；Key 侧：`middleware/distributor.go:613 SetupContextForSelectedChannel` 内的 `:677 channel.GetNextEnabledKey()`（`model/channel.go:206`） |
| 为什么可闭合 | pin 是一个**已存在的约束抽象**，支持多来源与优先级（`ResolvedPin` 还会记录被覆盖的 pin）。我们只需新增一个 pin 来源（供给授权）并把「已确定的渠道 + Key」注入上下文 |
| 实测支持 | A2：**定向渠道 6/6 成功，替身只看到该渠道的两把 Key（3/3 轮换），另一渠道的 Key 一次都没出现** → 「不被二次抽选」在底座现有机制上成立；渠道内 Key 池策略与「使用者选渠道、分享者选 Key」的分工天然吻合 |
| 必须修的前提 | pin 分支**跳过 token 模型限制**（`middleware/distributor.go:48-78` vs `:79-99`）→ 指定来源可绕过「允许模型」硬限制（TD-08，计划书 §5.2 第 1 条点名）。必须先把 pin/非 pin 收敛为**同一授权函数** |
| 风险 | pin 语义被任务原渠道锁定（`PinSourceOriginTask`）、亲和缓存、重试共用；改错会连带影响异步任务绑定 → 属**高风险扩展点（E2/E3）**，需要专门回归 |

### 1.3 资源授权（分享者归属 + ACL）→ **可闭合，但代价最高**

| 维度 | 判定 |
|---|---|
| 缺口 | 底座 `channels` **没有 owner 字段**（`model/channel.go:23-60`），渠道是全局资源（A1 实测：B 连渠道列表都看不到，因为整组挂在 `AdminAuth()` 下，`router/channel-router.go:21`） |
| 可闭合的理由 | ① 渠道结构支持扩展（新增 `apigx_channels` 影子表 + owner 字段，见 `schema-draft.md`）；② 授权判定所需的输入（平台 Key 范围、分组、供给）都在我们自己的新表里；③ 底座的用户/令牌隔离已验证可靠，不需要重做账号体系 |
| 代价 | 需要：新增领域表（27 张）+ 新增分享者接口（独立路由与鉴权）+ 修改 pin 授权分支 + 收紧任务产物默认策略 |
| 最大风险 | **TD-07**：底座令牌查找是**明文等值查询**（`model/token.go:290`，`middleware/auth.go:302-306`），且本地实测 `tokens.key` 落库确实是明文。计划书 §10.3 要求「平台 API Key 只存摘要、不可恢复」→ **必须在鉴权查找链路上加哈希分支**，这是写第一行业务代码前必须拍板的决策 |

## 2. 闸门结论

> **三条路径均在既有扩展点上可闭合，阶段 0 闸门通过，可以进入阶段 1。**

但附带两个**必须遵守的实施约束**：

1. **TD-07 已决策（按底座现状）**：平台 Key 沿用 `tokens.key` 明文存储与等值查找，**不改鉴权链路**。代价是偏离计划书 §10.3，已登记为已知风险；实施时必须保证明文不进入日志、错误响应与监控标签，并用 `authz` 的 `SecretView` 约束凭据可见性。
2. **TD-08 必须先修**：pin/非 pin 收敛为同一授权函数。否则阶段 1 的「指定来源」一上线就带着「绕过 token 模型限制」的缺陷（A2 已验证 pin 机制本身可用，缺陷在授权校验的缺失）。
3. **容量控制必须与计费预留解耦**：A4 实测「额度不超支」成立，但**没有并发上限**；新增并发控制时不得依赖 `effectiveQuota`（TD-09）。

同时确认：**额度类限制与计费原子预留是现成可复用的资产**（A4 实测：6 并发下恰好 1 个通过、额度未被击穿、被拒请求未出站），阶段 1 不需要重造这部分。

## 3. 阶段 1 工作包（详细任务）

按依赖排序；每项都标注了扩展点与验收方式。

| # | 工作包 | 关键扩展点 | 验收方式 |
|---|---|---|---|
| T1.1 | **平台 Key 接入（按底座现状）**：沿用 `tokens` 明文存储与等值查找，**不加哈希分支**；用 `authz` 的 `SecretView` 约束凭据可见性，确保明文不进入日志/错误/监控 | `middleware/auth.go:302-306`、`model/token.go:290`、`service/authz/permission.go` | 正常 Key 可用、错误 Key 401；接口与日志中均查不到明文；凭据可见性受权限约束 |
| T1.2 | **授权收敛（TD-08）**：pin/非 pin 走同一授权函数 | `middleware/distributor.go:48-78`、`service/channel_select.go:15` | 演示「固定来源 Key + 另一个渠道的请求头」不扩大授权 |
| T1.3 | **领域表落地（27 张）**：分享分组、渠道、供给、ACL、Grant、邀请等 | `apigx/model/`（新增） | **三库矩阵**：SQLite/MySQL/PG 各跑「全新库 + 从底座旧库升级 + 连续启动两次验幂等」 |
| T1.4 | **分享者接口**：受 owner 约束的分组/渠道/Key 池 CRUD | `apigx/api/`（新增，独立于 `router/channel-router.go`） | A 不能改 B 的渠道；普通用户不接触管理面 |
| T1.5 | **多 Key 导入与池策略**：批量导入、稳定凭据 ID、逐 Key 状态与统计 | `model/channel.go:182/673/725/738`、扩展点 E3 | 定向渠道内轮询/随机可用；Key 失效被跳过 |
| T1.6 | **免费计量（`usage_only`）**：新资金来源替换钱包前置 | `service/billing_session.go:377-476`、扩展点 E5 | 零余额用户可调用；成本估算为正；退款幂等；不产生负数 |
| T1.7 | **共享容量控制**：渠道/Key/账户池的并发、RPM/TPM、预算预留与对账 | `apigx/capacity/`（新增） | 满载渠道退出候选；并发下不超发；进程中断后租约可恢复 |
| T1.8 | **模型获取与供给发布**：一键获取 + 手工添加 + 待发布流程 | `controller/channel.go:1411`、`channel_upstream_update.go` 链路 | 新增模型进待发布而非自动扩大分享范围 |
| T1.9 | **广场与详情（只启用已完成能力）** | `web/src/features/apigx-*` | 同模型聚合为一个模型两项供给；私有供给不出现在计数与 `/v1/models` |
| T1.10 | **平台 Key 与指定来源**：Key 的允许模型/来源/固定来源/回退 | 扩展点 E2 | 「固定来源 Key 携带另一渠道请求头」不扩大授权（三种协议与旧入口一致） |
| T1.11 | **用量记录（使用者视角）**：请求、模型、实际渠道、耗时、估算成本 | 结算与日志链路 | 真实渠道与耗时可见；重试与流结束不重复计量 |
| T1.12 | **拒绝清单落地**：硬限制之外的错误码与不泄露 | `acl-state.md` §6 | 未授权供给返回 404；容量不足 429；无健康渠道 503 |

**本阶段明确不做**（计划书 §11）：质量自动路由（`auto` 默认值不得伪装完成）、价格同步与参考库、图片/语音/向量/重排/视频、邀请内测之外的公开注册。

## 4. 单人排期重估（用户口径：1 人主导 + AI 实现）

计划书 §11 的日历估算基准是 **2 名全职开发者**，并明确「单人开发不沿用双人排期」。现状与重估依据：

**有利因素**：环境已就绪（工具链/数据库/替身/验收脚本可复用）；设计已冻结（不需要边做边定方案）；底座复用面已定位到文件级；重复性工作（表结构、接口、脚本）可由 AI 批量产出。

**不利因素**：所有设计文档的「未核实」项需要在实现时补齐；三库兼容矩阵使每个迁移都要跑三遍；TD-07/TD-08 属于「先改底座再扩展」，带回归成本；本机磁盘已近满（D 盘 98.9%），大构建有风险。

**重估**（按工作包计，不给虚假精度）：

| 阶段 | 工作包数 | 单人+AI 粗估 | 说明 |
|---|---|---|---|
| 阶段 1 | 12 | **5–8 周** | 关键路径是 T1.1 → T1.2 → T1.3 → T1.6/T1.7；T1.3 与 T1.7 是三库矩阵与容量的重活 |
| 阶段 2 | — | 3–5 周 | 价格同步 + 质量路由，依赖阶段 1 的容量与路由骨架 |
| 阶段 3 | — | 4–7 周 | 六类能力联调，**受真实上游凭据到位的时点支配**，不是纯人力问题 |
| 阶段 4 | — | 1.5–3 周 | 压测、权限绕过检查、恢复演练 |

**校准建议**：上述估算是**区间而非承诺**。在阶段 1 完成 T1.1–T1.4 之后（约 2 周）用实际速率重新外推一次，比现在给精确数字更有意义。

## 6. 本评审的边界

- 全部结论来自**源码阅读与本地替身实测**；没有真实上游、没有压测、没有安全审计、没有在生产形态上验证。
- 「可闭合」是设计判断，**不代表已实现**；阶段 1 的实现仍需按上表逐项验收。
- 阶段 3 的排期受外部输入（真实上游凭据）支配，仅作参考。
