# 共享容量控制：核心账本（T1.7 第一部分）

对象：`new-api/apigx/capacity/`（包 `capacity`）。
依据：计划书 §9.2（先过滤再排序、原子预留与对账）、§11 阶段 1 验收；`docs/stage0/metering-state.md` §7；`docs/stage0/gate-review.md`（闸门约束）。

> **本工作包尚未完成**：本文件记录的是**核心账本**（已完成并验证）；把它接入请求路径（候选重选、全出口释放、长流续租、对账）属于下一部分，见 §5。

## 1. 为什么必须自建

阶段 0 已实测确认：底座**没有渠道/Key 级并发上限**——8 个并发请求的到达时间跨度仅 170ms（全部同时在飞）；`model/channel.go` 的选择互斥锁只保护「选择过程」，`middleware/model-rate-limit.go` 是**用户级**窗口限流。计划书 §9.2 的 [N4j] 判断在本机得到证实。

## 2. 设计（对应计划书 §9.2 的六条执行细节）

| 要求 | 实现 |
|---|---|
| **原子预留、全有或全无** | 一个 Lua 脚本：先对**全部维度**检查，全部通过后再**全部**扣减。任一维度不足则**不产生任何扣减**，返回 `*ErrExceeded{Dimension}` 供调用方重选 |
| **幂等归还** | 每次尝试有唯一 `attemptID`；预留时把「本次各维度占用量」写进租约 hash，释放时按记录值扣减并删除租约。重复释放直接返回（租约不存在 = 已释放），**不会减成负数** |
| **租约与崩溃恢复** | 所有计数与租约都带 TTL（默认 `LeaseTTL = 90s`）。进程崩溃后靠过期自动回收，不永久泄漏槽位。长流用 `Renew` 续租；`Renew` 返回 `false` 表示租约已失效，调用方必须按失败处理 |
| **多维度联合约束** | key 构造覆盖用户 / 平台 Key / 渠道 / 供给 / 上游 Key / **上游账户池**（后者是「多模型多渠道共用同一上游额度」的载体，防止切换模型或 Key 叠加容量） |
| **HTTP 并发与异步任务分开记账** | 并发槽位与 `AsyncTaskSlot` 是不同 key；计划书 §9.2 第 3 条要求分别记账 |
| **Redis 不可用时拒绝准入** | `New(nil)` 或 Redis 未启用时返回 `ErrRedisUnavailable`，上层据此**停止新准入**（不是放行）——「无法安全判断共享额度时不能从空计数恢复为全部空闲」 |
| **独立于计费** | 本包不读写钱包、不依赖 `effectiveQuota`。这是刻意的：底座 `shouldTrust` 在大额余额下会把 `effectiveQuota` 置 0 并跳过令牌预扣（TD-09），容量预留若挂在它后面会静默失效 |

输入校验：`attemptID` 必填、维度 key 必填、`Amount > 0`、`Limit >= 0`、**同一维度不得重复出现**（否则会被重复扣减）。

## 3. 验证（真实 Redis，8/8 通过，连续两次运行均通过）

命令：`APIGX_TEST_REDIS_ADDR=127.0.0.1:6379 go test ./apigx/capacity/ -count=1 -v`

| 用例 | 断言 | 结果 |
|---|---|---|
| `TestReserveWithinLimits` | 两次预留占 2 个槽位 | ✅ |
| `TestReserveIsAllOrNothing` | 一维已满时整体失败，**未生效的维度计数保持为 0** | ✅ |
| `TestReleaseIsIdempotentAndNeverNegative` | 连续释放三次，计数为 0 不变负 | ✅ |
| `TestLeaseExpiryRecoversCapacity` | 租约 1s 到期后计数自动回落，槽位可被重新抢占 | ✅ |
| `TestRenewExtendsLease` | 续租后不在原到期时间回落；租约不存在时返回 `false` | ✅ |
| **`TestConcurrentReserveNeverExceedsLimit`** | **40 个并发 goroutine 抢 limit=5 的槽位 → 恰好发放 5 个，计数=5** | ✅ **这是整套机制存在的理由；「先读计数再发送」在此必然失败** |
| `TestRejectsInvalidInput` | 空 attemptID / 空维度 / amount=0 / 重复维度 全部被拒 | ✅ |
| `TestReserveFailsClosedWithoutRedis` | 无 Redis 时返回 `ErrRedisUnavailable`（拒绝准入而非放行） | ✅ |

测试跑在 **Redis DB 15**、每个用例独立前缀，并在用例前后清理命名空间——因为计数带 TTL，跨运行的残留会互相干扰（首次实测就踩到了）。

## 4. 测试发现的两个真实缺陷（已修）

1. **`Usage` 把 `redis.Nil` 当错误**：`Release` 会把归零的 key 删掉、租约到期也会自动删除，因此「key 不存在」等于「占用 0」。原实现直接返回 `redis: nil`，会让上层把正常状态误判为故障。**这是代码缺陷，不是测试问题**。
2. **测试不是自洽可重复的**：计数带 TTL 存活于 Redis，第一次运行留下的值让第二次运行在第一句 `Reserve` 就失败。已改为「用例前清理 + 用例后清理」。**这提醒了一个真实运维点**：容量账本的状态是跨进程持久的，排查问题时不能假设从零开始。

## 5. 尚未完成（T1.7 第二部分）

核心账本本身可用且已验证，但**还没有接进请求路径**。剩余工作：

1. **接入候选选择循环**：先过滤（权限/能力/健康）→ 对候选做容量预留 → 失败则撤销本次未生效预留并**重选**；全部候选满载按计划书返回 `429`（可配置有上限的短路等待）。
2. **全出口释放**：正常结束、上游失败、客户端断开、panic 恢复都要释放；用 `attemptID` 保证幂等。
3. **长流续租**：流式请求按周期 `Renew`，并在 `Renew` 返回 false 时停止续租并记录。
4. **对账**：进程在「持久意图 → 容量 → 出站尝试」之间退出时的补偿（计划书要求的执行顺序中段）。
5. **与计费预留的顺序**：计划书顺序是「持久记录请求意图与预算预留 → 取得 Redis 容量 → 复验权限 → 记录出站尝试 → 发送」，接入时必须遵守，且**不得依赖 `effectiveQuota`**。
6. 把这些维度接到**具体配置**上（渠道/Key/账户池的并发与 RPM/TPM 上限来自 T1.3 的 `apigx_capacity_policies`）。
