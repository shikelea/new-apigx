# 共享容量控制：核心账本（T1.7 第一部分）

对象：`new-api/apigx/capacity/`（包 `capacity`）。
依据：计划书 §9.2（先过滤再排序、原子预留与对账）、§11 阶段 1 验收；`docs/stage0/metering-state.md` §7；`docs/stage0/gate-review.md`（闸门约束）。

> **本工作包尚未完成**：本文件记录的是**核心账本**（已完成并验证）；把它接入请求路径（候选重选、全出口释放、长流续租、对账）属于下一部分，见 §5。

## 1. 为什么必须自建

阶段 0 已实测确认：底座**没有渠道/Key 级并发上限**——8 个并发请求的到达时间跨度仅 170ms（全部同时在飞）；`model/channel.go` 的选择互斥锁只保护「选择过程」，`middleware/model-rate-limit.go` 是**用户级**窗口限流。计划书 §9.2 的 [N4j] 判断在本机得到证实。

## 2. 设计（对应计划书 §9.2 的六条执行细节）

| 要求 | 实现 |
|---|---|
| **原子预留、全有或全无** | 一个 Lua 脚本：先对**全部维度**检查，全部通过后再**全部**扣减。任一维度不足则**不产生任何扣减**，返回 `*ErrExceeded{Dimension}` 供调用方重选 |
| **幂等归还** | 每次尝试有唯一 `attemptID`；预留时把「本次各维度占用量」写进租约 hash，释放时按记录值扣减并删除租约。重复释放直接返回（租约不存在 = 已释放），**不会减成负数** |
| **租约与崩溃恢复** | 所有计数与租约都带 TTL（默认 `LeaseTTL = 90s`）。进程崩溃后靠过期自动回收，不永久泄漏槽位。长流用 `Renew` 续租；`Renew` 返回 `false` 表示租约已失效，调用方必须按失败处理 |
| **多维度联合约束** | key 构造覆盖用户 / 平台 Key / 渠道 / 供给 / 上游 Key / **上游账户池**（后者是「多模型多渠道共用同一上游额度」的载体，防止切换模型或 Key 叠加容量） |
| **HTTP 并发与异步任务分开记账** | 并发槽位与 `AsyncTaskSlot` 是不同 key；计划书 §9.2 第 3 条要求分别记账 |
| **Redis 不可用时拒绝准入** | `New(nil)` 或 Redis 未启用时返回 `ErrRedisUnavailable`，上层据此**停止新准入**（不是放行）——「无法安全判断共享额度时不能从空计数恢复为全部空闲」 |
| **独立于计费** | 本包不读写钱包、不依赖 `effectiveQuota`。这是刻意的：底座 `shouldTrust` 在大额余额下会把 `effectiveQuota` 置 0 并跳过令牌预扣（TD-09），容量预留若挂在它后面会静默失效 |

输入校验：`attemptID` 必填、维度 key 必填、`Amount > 0`、`Limit >= 0`、**同一维度不得重复出现**（否则会被重复扣减）。

## 3. 验证（真实 Redis，8/8 通过，连续两次运行均通过）

命令：`APIGX_TEST_REDIS_ADDR=127.0.0.1:6379 go test ./apigx/capacity/ -count=1 -v`

| 用例 | 断言 | 结果 |
|---|---|---|
| `TestReserveWithinLimits` | 两次预留占 2 个槽位 | ✅ |
| `TestReserveIsAllOrNothing` | 一维已满时整体失败，**未生效的维度计数保持为 0** | ✅ |
| `TestReleaseIsIdempotentAndNeverNegative` | 连续释放三次，计数为 0 不变负 | ✅ |
| `TestLeaseExpiryRecoversCapacity` | 租约 1s 到期后计数自动回落，槽位可被重新抢占 | ✅ |
| `TestRenewExtendsLease` | 续租后不在原到期时间回落；租约不存在时返回 `false` | ✅ |
| **`TestConcurrentReserveNeverExceedsLimit`** | **40 个并发 goroutine 抢 limit=5 的槽位 → 恰好发放 5 个，计数=5** | ✅ **这是整套机制存在的理由；「先读计数再发送」在此必然失败** |
| `TestRejectsInvalidInput` | 空 attemptID / 空维度 / amount=0 / 重复维度 全部被拒 | ✅ |
| `TestReserveFailsClosedWithoutRedis` | 无 Redis 时返回 `ErrRedisUnavailable`（拒绝准入而非放行） | ✅ |

测试跑在 **Redis DB 15**、每个用例独立前缀，并在用例前后清理命名空间——因为计数带 TTL，跨运行的残留会互相干扰（首次实测就踩到了）。

## 4. 测试发现的两个真实缺陷（已修）

1. **`Usage` 把 `redis.Nil` 当错误**：`Release` 会把归零的 key 删掉、租约到期也会自动删除，因此「key 不存在」等于「占用 0」。原实现直接返回 `redis: nil`，会让上层把正常状态误判为故障。**这是代码缺陷，不是测试问题**。
2. **测试不是自洽可重复的**：计数带 TTL 存活于 Redis，第一次运行留下的值让第二次运行在第一句 `Reserve` 就失败。已改为「用例前清理 + 用例后清理」。**这提醒了一个真实运维点**：容量账本的状态是跨进程持久的，排查问题时不能假设从零开始。

## 4.5 接线（T1.7 第二部分）与运行时 A/B 验收

**接线位置**：`middleware/distributor.go` 在 `SetupContextForSelectedChannel` 之后、`c.Next()` 之前。

选这里有三个理由：① 此时渠道已确定（无论 pin 还是自动选路），**两条路径共用同一处**；② 在 `c.Next()` 之前注册 `defer`，释放发生在**下游（含流式响应）全部结束之后**；③ 不需要改动 relay 内部任何逻辑。

**默认关闭**：`APIGX_CAPACITY_ENABLED` 未设置时整个钩子直接返回，既有链路行为完全不变。渠道并发上限当前来自 `APIGX_CHANNEL_CONCURRENCY_LIMIT`（**过渡方案**，最终应来自 `apigx_capacity_policies`）。

**验收脚本**：`tools/stage1-verify/capacity-limit.mjs`（让替身把每个请求握 1.5 秒以制造真实重叠）。

| 检查项 | 阶段 A（默认关闭） | 阶段 B（上限=1，并发 3） |
|---|---|---|
| 状态分布 | **200×3**，429×0 | **200×1，429×2** |
| 到达上游次数 | 3 | **1**（被拒的没有出站） |
| 429 是否带 `Retry-After` | — | ✅ `Retry-After: 1` |
| 响应体 | — | `{"error":{"code":"capacity_exceeded",...}}`（脱敏，不含内部维度） |
| 结果 | **2/2 通过**（既有链路未被改变） | **4/4 通过** |

**槽位归还验证**：并发打完后用 Redis `--scan --pattern 'apigx:cap:*'` 检查——**没有任何残留 key**（计数归零即删、租约已删）；紧接着再打一轮仍然正常（1 通过 + 1 被拒），说明**容量可复用、没有泄漏**。

**单元/集成测试**：`apigx/capacity` 8/8、`apigx/relayhook` 6/6（真实 Redis）。接线测试里刻意覆盖了「默认关闭时不产生租约」「未配置上限时不约束」「满载 429+Retry-After」「重复释放幂等」「Redis 不可用 503」「长流续租」六个场景。

**三个真实缺陷（均由测试发现并修复）**：
1. `Acquire` 起初收 `int64`，而底座 `Channel.Id` 是 `int` → 编译期就暴露，改为 `int` 并在内部转换。
2. **测试清理时机错误**：同一用例里多次替换 `common.RDB`，先注册的清理最后执行，届时客户端已关闭 → `Drop` 报 `client is closed`。已改为「每个用例只建一次客户端 + 允许重复创建的 gin 上下文」。
3. **TTL 粒度陷阱**：TTL 以**秒**下发（`ttl/time.Second`），测试用 1500ms 实际被截断成 **1 秒**，比续租间隔（`ttl/3`）还短，续租必然失败并误报「租约已过期」。已在代码注释里写明「必须用整秒且明显大于续租间隔」，测试改用 3 秒。

## 5. 仍未完成（T1.7 剩余部分）

已完成的部分：**核心账本**、**渠道并发接线**、**四态限制解析**（`apigx/capacity/policy.go`）、**多维度联合预留**（渠道 + 平台 Key + 用户）。

### 5.1 多维度与四态（已完成）

- **四态解析**（`capacity.Policy` / `capacity.Resolve`）：`未配置 / 禁用 / 继承 / 明确不限 / 明确值` 五值语义按 CODE_STYLE 第 11 条实现，并**校验「模式 + 值列」的配对**（`明确值` 必须 > 0，其余必须为 0）。解析沿「最具体 → 最一般」的链进行，`明确值`/`明确不限`/`禁用` 立即终止，`继承`/`未配置` 继续向上查找；整条链都未配置时返回 `Unset`——**调用方不得把它当成「不限」**（有专门的测试守住这条）。
- **多维度联合预留**：接线层从 gin 上下文取 `channel_id` / `token_id` / `id`，为每个维度解析限制并放进**同一次原子预留**。任一维度满即整体拒绝。
- **运行时验证**：只设 `APIGX_TOKEN_CONCURRENCY_LIMIT=1`（**渠道不设限**），并发 3 → **200×1 + 429×2、上游仅 1 次、Redis 零残留**。这证明多维度确实生效，而不是只有渠道维度在起作用。
- 顺带修掉一处**对外措辞误导**：429 的消息原写作 "channel capacity is temporarily exceeded"，但超限的可能是平台 Key 或用户维度，已改为中性的 "capacity is temporarily exceeded"（精确维度只进内部日志）。

### 5.2 仍未完成

1. **候选重选**：当前渠道满载就直接 429。计划书要求先在候选集中重选合格渠道，全部候选都满才返回 429——这需要把「选择」与「预留」合并成一个循环（属于对 `Distribute` 的更深改动，风险最高，故留到最后）。
2. **上游 Key 与上游账户池维度**：账本已支持，但接线层还拿不到这两个 ID——需要「渠道 → Key / 所属账户池」的映射（属于 T1.3 的 `apigx_upstream_keys` / `apigx_upstream_accounts`，其仓储层尚未实现）。这是**防止容量叠加的关键维度**，优先级高。
3. **RPM/TPM 与预算维度**：key 构造与账本都就绪，但需要token 预估与窗口口径的产品决策，且 TPM 预留必须用可执行的输出上限（计划书 §9.2）。
4. **上限来源**：仍是环境变量。应改为从 `apigx_capacity_policies` 读取，并把「未配置」的过渡行为（当前=不约束）替换为显式策略。
5. **对账**：进程在「持久意图 → 容量 → 出站尝试」之间退出时的补偿逻辑尚未实现。
6. **异步任务槽位**：`AsyncTaskSlot` 的 key 已备好，尚未接入任务提交路径。
