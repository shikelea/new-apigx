# 分享者接口与凭据加密（T1.4 / T1.5 起步）

对象：`new-api/apigx/{api,route,secretbox}`（我们的代码）+ `router/api-router.go` 的一处接线。

## 1. 做了什么

| 文件 | 内容 |
|---|---|
| `apigx/secretbox/secretbox.go` | 上游凭据的静态加密封装：AES-256-GCM + 版本化信封 `enc:v1:<nonce>:<密文>`；主密钥来自 `APIGX_SECRET_KEY`（64 位 hex），**与数据库分离**；缺主密钥时**失败关闭** |
| `apigx/api/share.go` | 分享者接口：分享分组 / 渠道 / 上游 Key 池的 CRUD。每次请求从登录态取 owner，**不接受客户端提交的 owner** |
| `apigx/route/route.go` | 路由注册入口，挂载前缀 `/api/apigx` |
| `router/api-router.go` | 上游接线 4 行：独立路由组 + `UserAuth` + `apigxroute.Register`（台账 D-012） |

**接口与底座既有管理接口的关系**：完全独立。底座的 `/api/channel` 整组挂在 `AdminAuth()` 下且渠道是全局资源，不能作为分享者接口复用。

**凭据处理**（这是本工作包最要紧的部分）：

- 明文只在请求体里出现一次 → 服务端立即加密 → **数据库只存信封**；
- 响应**从不回显**明文，也**不回显信封**（信封本身也是凭据材料），只给 `****1234` 这样的脱敏提示；
- 列表接口只输出状态类字段与 `usable` 判断；
- 主密钥未配置时创建 Key 返回 **503 并拒绝写入**（不退化成明文存储）。

## 3. 测试发现的三个真缺陷（都已修）

1. **`base_channel_id` 唯一索引与 0 值冲突**（仓储层测试）：该列有唯一索引，但新建时为 0 → **两条未绑定渠道互相冲突**。已改为强制 `BaseChannelID > 0`（每个分享渠道必须绑定一条底座渠道，转发链路也需要它）。
2. **渠道可以挂到别人的分组下**（接口层测试）：`CreateChannel` 只校验了 owner 非零，**没有校验分组归属** → 只要知道别人的分组 ID 就能把自己的渠道挂进去。已加归属校验（返回 `ErrNotFound`，对外与不存在等价）。这是**越权漏洞**，不是小问题。
3. **`deleted_at` 写入了整数 epoch**（真实 PG 端到端才发现）：
   ```
   postgres error SQLSTATE 22008: 日期/时间值超出范围: "1789565408"
   ```
   `deleted_at` 是 `gorm.DeletedAt` → PG `timestamptz`、MySQL `datetime`；而表里其它 `*_at` 列是 `int64`。**SQLite 类型宽松会静默接受，只有真实 PG 能暴露**。已改为写入 `gorm.DeletedAt{Time: ...}`。
   → 这条正是三库/真实实例验证存在的意义：如果只跑 SQLite，它会一直潜伏到上线。

## 4. 一个测试自身的缺陷（也要记）

`TestDecryptRejectsTamperedCiphertext` 起初通过替换 base64 的**最后一个字符**来伪造篡改，但 RawURL 编码的末字符可能有被忽略的比特 → **解码结果没变**，"篡改"没发生，测试变成偶发通过/失败（它在上一轮突然失败才被发现）。已改为**确定性翻转解码后的字节**。教训：篡改类测试必须断言"被改动的字节确实变了"。
