## 1. 审查目的与证据边界

本轮回答四个问题：现有实现是否真正复用了 New API、计划中的核心产品链路是否闭环、现有验收是否可信，以及接手后应按什么顺序整改。本轮只修改审查与状态文档，不修改业务代码。

结论来自当前源码、Git 差异、可重建演练、本地测试和 MySQL 迁移实测。它不能替代真实第三方上游、生产多实例、持续压测或正式安全测试。历史文档中的“31/31”“全部通过”“未发现产品回归”只代表当时选定脚本或局部用例的结果，不能继续作为上线结论。

本机 MySQL 验证只使用本地凭据，凭据不进入仓库、文档、日志或提交记录。

## 2. 接手结论

现有版本已经搭出了较完整的领域骨架，也正确复用了 New API 的厂商适配、模型抓取、账户/令牌、中继、计费会话、任务插件和部分前端组件。阶段 C 已从锁定基线顺序应用 162 个补丁，重建 tree `65876bdc7f1eceb528d47ddc7d4dbcf2d45493c5` 与当前 fork 完全一致，说明交付不是不可追溯的散乱快照。

阶段 B1 已把资源 ACL 接入全部已知出站入口，阶段 B2 已修复管理员跨 owner 审核，阶段 B3 已关闭渠道创建、供给发布能力投影和删除/停用的原子生命周期缺口，阶段 B4 已让空值/`auto` 真正按 6 小时可靠性、延迟、文本吞吐与实时容量综合选路。阶段 C 又关闭了稳定多 Key、凭据版本、异步任务终态与租约恢复缺口。项目仍需完成阶段 D、前端任务流与生产验证后才能上线。

接手时应保留 New API 作为底座，避免重写适配器和中继；同时把 APIGX 从“旁路表 + 多处分散钩子”收敛为少数明确的领域服务和出站闸门。

## 4. 已确认问题

### P0：上线阻断

#### P0-1 资源 ACL 没有进入真实转发链路（阶段 B1 已关闭）

统一授权快照现已合并 owner、公开可见性、有效 Grant、资源存活/发布状态和平台 Key 范围，并在固定来源、自动/策略、亲和、随机、重试、异步任务、Midjourney、Responses WebSocket 与历史任务上游代理出站前复验。身份矩阵、拒绝脱敏、本地真实网关和全仓回归已通过；真实第三方上游与生产多实例仍属于上线前验证边界。

#### P0-2 默认 `auto` 没有使用 APIGX 质量路由（阶段 B4 已关闭）

空值与 `auto` 现在都进入 `StrategyAuto`，在资源 ACL、熔断和当前容量过滤之后，按 6 小时可靠性、延迟、文本吞吐和容量余量综合排名，只把最高名次交给底座选路。计算失败或无候选时返回空 allow-list，不再静默退回随机；最终优胜集合不缓存，容量策略更新也会立即清除准入策略缓存。最终二进制真实 HTTP 已验证五种策略均只选质量更优来源、满载时切到次优来源、释放后立即恢复。

#### P0-3 管理员无法审核其他用户的供给（阶段 B2 已关闭）

管理员现可从 `GET /api/apigx/reviews/offerings` 读取跨 owner 待审核队列，并按资源 ID 发布或驳回；分享者 CRUD 仍保持 owner 隔离。状态转换使用条件更新，审核与脱敏不可变审计事件同事务提交。真实 HTTP 13/13、审计唯一性、SQLite/MySQL/PostgreSQL 行为矩阵与全仓回归已通过。

#### P0-4 渠道创建与删除不是一个原子生命周期（阶段 B3 已关闭）

普通用户现只能提交自助配方，不能猜测并绑定全局底座渠道。底座渠道、APIGX 渠道和初始加密 Key 同事务创建；供给审核状态、不可变审计、底座模型和能力也同事务提交。删除先独立停用底座渠道与能力并刷新缓存，再幂等清空明文 Key、模型、多 Key 状态和能力，最后软删领域渠道。创建与发布逐步骤故障注入、重复删除、SQLite/MySQL/PostgreSQL 生命周期矩阵、真实 HTTP 15/15 和删除后数据库六项状态均通过。阶段 C 已让已提交任务继续使用绑定的历史凭据，并按原任务租约收尾。

#### P0-5 验收脚本会产生假绿（阶段 A 已关闭）

- `tools/stage0-verify/acceptance.mjs:426-437` 会汇总 `FAIL`，但没有设置非零退出码。
- `tools/stage2-verify/route-strategy.mjs`、`weight-distribution.mjs`、`key-weight-distribution.mjs` 的普通断言只打印红色 `FAIL`，只有异常才 `exitCode=2`。
- `tools/stage2-verify/tpm-adjust.mjs` 只写出待核对状态，最终结论依赖外部人工读取 Redis。

阶段 A 已统一断言计数和退出码：普通断言失败返回 1，基础设施异常返回 2；五个脚本的受控失败均实测退出 1。TPM 脚本现在按唯一模型和开始时间定位本次用量，直接读取测试渠道的 Redis 分钟桶并断言；开启/关闭调整的真实结果分别为 46/46 与 8204/46（Redis/实际 token）。

因此脚本退出 0、文档写“有结论”或“全部通过”不能作为机器验收。所有验收入口必须满足：任何断言失败即非零退出、缺少依赖明确 skip/blocked、结果可在一次命令中闭环。

### P1：核心能力未闭环

#### P1-1 加权多 Key 的故障隔离按槽位而不是稳定 Key（阶段 C 已关闭）

每把真实 Key 现在只投影一个槽位，稳定 Key ID 与原生权重一同进入 `ChannelInfo`。底座健康、容量和熔断分别保存来源并合并成兼容状态，增删/重排后状态仍跟随稳定 ID。3:1 轮询分布、单 Key 隔离和来源独立恢复均已通过自动化与真实 HTTP 验收。

#### P1-2 异步任务快照只有写入，没有完整生命周期（阶段 C 已关闭）

异步任务现在固化用户、底座令牌、供给、渠道、稳定 Key、凭据版本、容量/价格版本和租约。轮询按历史凭据分组，Key 轮换并删除活动 Key 后旧版与新版任务仍可完成；状态以旧状态条件更新并检查 CAS 结果，终态只释放一次。快照写失败先落无密钥持久修复事件，重启对账恢复续租。取消端点只接受明确实现适配器契约的上游，当前内置视频适配器返回稳定 501 能力限制。

#### P1-3 模型价格一键匹配未形成用户流程

`ReadModelPriceFromBase` 和 `ReadModelPriceFromBillingExpr` 只有定义，没有调用方。`POST /channels/:id/price-sync` 还要求客户端提交完整 `readings`：`new-api/apigx/api/share.go:1723-1765`；分享前端没有调用此接口。当前只有底座全局同步和人工覆盖，尚不能在抓取模型后按模型 ID 一键匹配 New API 自带价格。

#### P1-4 六类 AI API 的用量与估算成本不完整

事件模型预留了通用 `quantity_milli`，但运行时 `RecordSettlementUsage` 只写输入/输出 token：`new-api/apigx/relayhook/usage_record.go:26-89`。图片张数、音频时长、视频时长/任务、向量、重排没有统一进入 `apigx_usage_events`。分享者摘要主要从 attempts 聚合请求数、成功失败和延迟，无法完整显示真实用量与估算成本。

#### P1-5 关键能力默认关闭且没有部署基线

容量、`usage_only`、逐 Key 统计、质量统计、熔断、质量策略和 TPM 调整均由环境开关控制，其中多项默认关闭。根目录 `.env.example` 只列出基础环境、币种、密钥和代理，没有给出产品所需的正式开关组合；启动时也没有检查“免费共享模式却未启用 usage-only”等矛盾配置。

#### P1-6 前端组件和渠道能力复用不完整

`invite-card.tsx`、`group-create-dialog.tsx`、`channel-create-dialog.tsx` 直接使用原生 `<select>`，不符合 `web/AGENTS.md` 的组件复用要求。普通分享者自助建渠道只允许 OpenAI、Anthropic、Gemini：`new-api/web/src/features/share/components/channel-create-dialog.tsx:91-117`、`new-api/apigx/api/share.go:2097-2106`，与底座已经支持的图片、语音、视频和其他任务型渠道不一致。

#### P1-7 前端页面存在，但真实任务流没有闭环

这不是视觉风格问题，而是信息架构和操作路径仍按后端表结构拼装：

1. `/share` 把分组、渠道、邀请发放/兑换和消耗汇总依次堆在一张长页面里；分组与渠道是两张平行表，用户看不出“某分组下有哪些渠道、还差哪些步骤才能发布”。
2. `/share/:channelId` 只能抓模型、设置容量和提交供给。Key 表没有新增、轮换、停用、删除、改权重入口；供给表显示原始 `price_rule_id` 和逗号拼接的能力值，没有价格匹配、发布阻塞原因和下一步动作。
3. “选择模型”和“一键同步全部模型”并列，批量导入逐项串行请求，页面不呈现每个模型的成功、重复、待定价或失败结果。
4. 平台 Key 的来源设置要求用户手填 offering ID、模型 ID、owner 数字 ID：`new-api/web/src/features/keys/components/dialogs/apigx-scope-dialog.tsx`。模型广场已经有分享来源数据，却没有把选择结果直接带入该表单。
5. 管理页要求管理员手填渠道 ID、作用域 ID和模型名，无法从待审核队列、价格冲突或异常资源直接处理；即使后端修好跨 owner 审核，现有界面仍不可正常运营。
6. 分组详情先取广场前 100 条再在浏览器过滤，模型广场的分享来源也只取前 100 条；数据增长后会静默缺项。分组页还把分享者显示为 owner 数字 ID。
7. 多数 mutation 只刷新查询或关闭弹窗，没有统一成功、失败、部分成功和可重试反馈；“删除渠道后停止服务”等文案目前还先于后端事实。

前端改造必须等阶段 A-D 的接口和状态机稳定后开始，否则会继续围绕错误语义返工。

### P2：工程与维护风险

1. ~~全仓 Go 测试在 Windows 上没有可靠绿色基线。~~ 阶段 A 已改用进程内原子序列隔离亲和缓存键，并关闭每次 `InitDB/InitLogDB` 新建的 SQLite 句柄；根模块全仓回归现已通过。HTTP/2 负例也改为断言可观察契约，避免绑定 Windows socket 内部错误文案。
2. `controller` 的 SQLite 测试数据库未统一注册关闭清理，`setupSecurityEnrollmentTest` 关闭主 DB 但没有关闭独立 `LOG_DB`，组合运行会出现临时文件占用并最终超时；原始基线也能复现相关失败。
3. 部分任务测试会触发 `WHERE conditions required`，夹具使用零 ID 任务却把红色数据库日志当作噪声，应改成明确夹具或断言。
4. `docs/stage0/upstream-diff.md`、`docs/stage4/README.md`、`PROJECT_STATUS.md` 的差异数量和验收结论互相冲突，旧文档不能继续作为交接依据。
5. 本机 MySQL 8.0.12 的 `@@default_storage_engine` 为 MyISAM。APIGX 自有表显式 InnoDB 的迁移和幂等已经通过，但 New API 全站表仍可能因默认引擎导致索引错误；正式开发和部署基线必须要求 InnoDB。

## 6. 接手优化路线

以下阶段按依赖排序。阶段 A-D 先稳定后端权限、生命周期、任务、价格、计量和路由语义；随后基于真实任务流重做必要前端，最后完成运维交付。后端接口未定稿前不扩 UI。

### 阶段 A：恢复可信工程基线（2026-09-18 已完成）

目标是让每个后续结论都能被自动化复核。

1. [x] 修复五个假绿脚本，统一结果收集器和退出码；TPM 用例自己读取 Redis 并断言。
2. [x] 修复上游 Windows 测试隔离：唯一键改用单调计数，SQLite 主库与 `LOG_DB` 都注册关闭清理，并保留并发语义。
3. [x] 新增正式部署配置模板，列出 APIGX 所有开关、推荐值和依赖；启动时对互斥/缺失组合失败关闭。
4. [x] 把 MySQL InnoDB、Redis、加密主密钥、usage-only、质量采集和路由策略纳入启动自检，并补齐 Redis 3 缓存写入兼容。

**退出门槛**：全仓测试在支持的平台稳定通过；每个验收脚本失败时返回非零；配置缺失能在接流量前被发现；CI 不再引用“31/31”文本判断结果。

### 阶段 B：修复 P0 权限与资源生命周期

1. [x] 建一个统一的 `AuthorizeForOutbound`/候选服务，输入调用者、平台 Key、模型、供给、渠道和尝试上下文。
2. [x] 候选顺序固定为：资源存在且发布 → 可见性/Grant → 平台 Key 来源约束 → 能力匹配 → 容量预留 → 熔断与质量排序。
3. [x] 公开、邀请码/指定用户、仅自己三种模式都在真实转发、固定来源、自动路由、亲和缓存、重试和异步任务原渠道上执行同一授权规则。
4. [x] 审核接口改成 reviewer-scoped 操作：先验证管理员角色，再按资源 ID 跨 owner 读取；审计记录审核人、资源 owner、前后状态和理由。
5. [x] 将“建底座渠道 + 建 APIGX 渠道 + 加密 Key + 能力投影”做成事务加补偿的 saga；删除先停止新流量，再停用底座渠道、撤销能力/Key 投影、清缓存，最后软删领域对象。

**退出门槛**：建立 owner、指定用户、邀请码用户、无授权用户四类身份的正反用例；任何入口都不能调用不可见资源；注入每个创建步骤失败都不留可转发孤儿渠道；删除后新请求必定失败且已有任务按明确策略收尾。

### 阶段 C：重做多 Key 与异步任务闭环

1. [x] 选择 Key 时使用稳定 Key ID 和权重算法，不再用复制明文槽位表达权重。
2. [x] 熔断、冷却、统计和禁用都按稳定 Key ID；同一 Key 的所有权重份额同时隔离。
3. [x] 异步任务提交时固化稳定 Key ID、凭据版本、供给、价格版本和容量租约；查询/取消走任务快照，不读取“当前渠道 Key”。
4. [x] 实现任务状态单向推进、终态释放、超时对账、取消和持久修复队列；真实进程中断后由新进程接管租约并完成任务。

**退出门槛**：权重分布、单 Key 失败隔离、Key 轮换后查询、删除 Key 后查询、取消、进程崩溃恢复和重复回调全部有自动化用例。

### 阶段 D：完成价格、计量和综合自动路由

1. 抓取模型后优先读取 New API 本地 `/api/pricing`/ratio 配置与计价表达式，再按可配置来源读取 `okmoyan.com/llms.txt`、ModelRadar 等外部源；所有来源先预览差异，人工确认后产生不可变价格版本。
2. 模型 ID 匹配采用规范化名称、别名和人工确认，不能仅做模糊字符串命中；未知价格保持 `unpriced`，不能写成 0。
3. 为对话、图片、语音、向量、重排、视频分别定义真实计量维度和单位，保留源币种、汇率来源/时间/版本与价格快照；默认展示 USD。
4. 实现真正的 `auto`：先过授权与容量硬条件，再综合延迟、吞吐、6 小时可靠性和可选成本；缺指标时采用明确降级规则并给出可解释结果。
5. 分享者用量页改读统一用量事件，展示请求、真实数量、估算成本、未定价数量和失败重试，不从 attempts 推断不存在的用量。

**退出门槛**：六类 API 各有一条真实或可控替身用量闭环；价格版本可追溯；历史成本不随新价格/汇率改写；`auto` 与三种单指标策略的路由结果可解释、可回放。

### 阶段 E：按真实使用逻辑重做必要前端

阶段 E 在 A-D 的后端契约冻结后开始。先做一次带真实数据的页面回扫，再按三类角色组织信息，不按数据库表或现有组件分组。

#### E1 分享者任务流

1. “我的分享”以分享分组为主层级，展开后看渠道、模型、授权和用量；邀请兑换属于使用者入口，邀请发放属于分组管理，不再混成一个无层级长页面。
2. 渠道采用可恢复的发布向导：基本信息 → 多 Key 与轮询/权重 → 抓取或手填模型 → 一键匹配价格 → 容量限制 → 提交审核 → 发布。页面始终显示当前步骤、阻塞原因和下一步。
3. Key 池补齐新增、轮换、停用、删除、权重、过期时间、最近成功/失败和冷却状态；危险操作显示真实影响范围。
4. 模型导入使用一次批量接口和逐模型结果，明确区分已导入、重复、别名待确认、价格未知、协议不支持和上游抓取失败。
5. 消耗页使用阶段 D 的统一事件，按渠道/Key/模型显示请求、真实单位、估算成本、未定价和失败重试。

#### E2 使用者任务流

1. 保留 New API 模型广场作为统一入口，同模型聚合多个分享来源；模型详情展示分享名称、分享者展示名、协议能力、价格、延迟、吞吐、6 小时可靠性、样本是否充分和可用状态。
2. 用户可在模型详情直接选择“系统自动、最低延迟、最高吞吐、最高可靠性、指定来源”，无需复制 offering/owner 数字 ID；选择结果写入指定平台 Key。
3. 邀请码兑换成功后直接进入获得授权的分组或模型，不跳到泛化价格页；无权限、已撤销、待审核、暂停、无可用渠道分别给出可行动的状态。
4. 广场、分组详情和来源列表改用服务端分页/筛选，不再读取前 100 条后在浏览器过滤。

#### E3 管理员任务流

1. 建待审核队列，显示分享者、分组、渠道、模型、价格来源、权限范围、风险和变更差异；审核不要求手填渠道 ID。
2. 价格管理从具体模型/渠道/Key 进入，展示自动匹配来源、冲突、人工覆盖和版本历史，不要求手填 scope ID。
3. 路由运营从模型进入，先预览候选与影响，再发布策略；展示综合 `auto` 的选择理由和降级原因。
4. 提供异常资源视图：孤儿底座渠道、凭据错误、价格未知、质量样本不足、熔断、积压任务和对账失败均可定位到处理动作。

#### E4 交互与组件约束

1. 复用 New API 的表单、选择器、数据表、对话框、错误状态、权限和国际化组件，移除原生 `<select>` 与重复 API 封装。
2. 后端返回渠道配方、能力、状态和允许动作；前端不硬编码三种协议，也不根据数字状态猜业务动作。
3. 所有 mutation 统一呈现成功、失败、部分成功、重试和幂等结果；加载、空、无权限、待审核、暂停、未定价、降级和不可用都有独立状态。
4. 先完成桌面与移动端任务流原型，再接 API；只对关键流程写交互测试，最后用真实浏览器完成三角色验收。

**退出门槛**：分享者能从空账号完成一次发布，使用者能从广场选择自动或指定来源并完成调用，管理员能从队列完成跨 owner 审核和异常处置；全程不输入内部数字 ID，刷新后状态一致，失败步骤可恢复，桌面和移动端浏览器验收通过。

### 阶段 F：协议覆盖与运维交付

1. 由后端返回可用渠道配方，按底座实际能力逐步开放图片、语音、向量、重排、视频，并让前端支持矩阵与真实行为一致。
2. 建上线基线：指标、告警、审计、备份恢复、上游升级清单、数据迁移回滚、容量压测与故障演练。

**退出门槛**：六类 API 的支持矩阵与实际一致；关键告警可送达；锁定基线升级与回滚演练可重复执行。

接手后的第一个开发批次只做阶段 A 与阶段 B 的最小闭环：

2. [x] `A2`：补完整配置模板与启动自检。
3. [x] `B1`：建立统一出站授权对象和 ACL 矩阵测试，先堵住非公开资源绕过。

5. [x] `B3`：实现渠道创建补偿与删除停用。
