# 代码风格与工程约定 · apigx

> 由开发流程维护（§5）。Google Go Style 为主，下列为本项目在实战中反复验证过的补充约定。

## 一、改文件：先读真实文本，改完必须校验

- **禁止凭记忆写补丁锚点**。`gofmt` / Prettier 会重排空格与对齐，锚点极易失效。
- 补丁脚本**必须校验**：替换后检查目标文本确实存在，否则拒绝写盘并报错。
  > 教训：曾出现"脚本打印成功但替换静默未生效"，导致接口字段为 `nil`，靠用例才发现。
- 含引号/反引号/模板串的代码，**不要用 shell here-string 承载**（PowerShell 会破坏转义）；
  改为用文件写入（`write`）或写入独立文件（如新 `.go` 文件）。
- 写库 SQL 同理：**先读列定义与外键**，再写语句；JSON 值用文件 + `psql -f`，不要经过 shell 引号。

## 二、测试与断言

- **取数据要按身份，不按下标/顺序**。列表常按 `id DESC`，用 `items[0]` 会取错行。
- 断言要先确认**语义**再写：曾把"3 条候选"写死，而幂等去重后实际是 2 条。
- 并发相关的**安全属性必须有用例**：如"并发兑换单次邀请只能有一个成功"。
- 既有用例断言的是**产品口径**：改动使它失败时，**先假设测试是对的**，再论证是否真的要改口径。
  > 教训：曾把广场判据改成"公开 或 本人所有"，被既有用例拦下 —— 广场是发现面，所有者看自己的东西走「我的分享」。

## 三、领域约定（apigx）

- **两套枚举不可混用**：邀请范围 `1=分组/2=供给`，授权资源 `0=分组/1=供给`。转换必须显式。
- `apigx_*` 表的软删是 `alive_flag = 本行 ID` + `deleted_at timestamptz`（**不是** epoch 整数）；
  底座 `channels` **没有**软删列（硬删除），且 `tasks.channel_id` 有外键，删渠道前必须先清引用它的任务。
- **凭证只存哈希**，明文只在创建响应里出现一次，**不得**进入列表接口、日志与错误信息。
- 授权/邀请类接口的越权一律返回 **404**（不确认"资源存在但不属于你"），失败原因不区分以防枚举。

## 四、收录纪律

- 未验证的内容**不得**写成"已验证"；失败与回退必须如实记录（含"未解"）。
- 每个上游改动登记到 `docs/stage0/upstream-diff.md`（D-编号）。
## 五、构建与验证（**最容易坑到用户的一条**）

- **前端改动必须重建后端二进制才能被用户看到**：`main.go` 用 `//go:embed web/dist` 把前端**嵌进二进制**，
  网关服务的是**编译那一刻**的产物，不是磁盘上的 `dist`。
  ⇒ 正确顺序固定为：`cd web && bun run build` **然后** `go build -o .../new-api.exe .` **再**重启。
  > 教训：曾只重建前端就告诉用户"刷新即可"，导致用户长时间看到旧界面
  > （本地 dist 是 `index.2a6ec5d43e.js`，网关却返回 09:34 那次构建嵌进去的 `index.c17841c7a5.js`），
  > 用户连续报告"改了还是老样子"。**判断方法**：对比 `web/dist/index.html` 与 `curl /` 引用的 `index.*.js` 哈希。
- 前端改动只有 `dist` 变了、exe 没重建时，**刷新浏览器毫无作用**（不是缓存问题）。
- 报"界面没变化"之前，先做上面那个哈希对比，不要先让用户清缓存。
## 六、i18n 语言文件的**层级**（踩过的坑）

- 语言文件结构必须是 **`{ "translation": { 键: 文案 } }`** ✓（i18next 的资源结构是 `{ 语言: { 命名空间: 键 } }`）。
- **新增键必须写进 `translation` 里** ✗ 不能写在 JSON 顶层：顶层散键会被 i18next 当成**命名空间名**，
  于是 `t('usage.title')` 在 `translation` 里查不到 ⇒ **原样回显键名**。
- 本项目**键就是英文原文** ✓，所以这个 bug 很隐蔽：查不到时回显的英文看着正常 ✓，
  只有**带点的键**（`usage.title`、`taskCenter.title`）一眼露馅 ✓。
- 用脚本批量加键时，务必 **`json.translation[key] = value`** ✗ 而不是 `json[key] = value`；
  写完**校验**：`Object.keys(json)` 应当**只有** `translation`。
- 回归用例：`web/src/i18n/__tests__/dotted-keys.test.ts`（守住"顶层只有 translation"与"带点键能解析"两条）。
## 七、验收脚本的使用次序（踩过的坑）

- `tools/stage3-verify/*.mjs` 是**两阶段**脚本：`--phase setup` 自建夹具 → **等约 60 秒**（底座同步能力索引）→ `--phase verify`。
- **不能跳过 setup 直接 verify** ✗：会得到大量 503 `No available channel for model ...`，
  看起来像回归，其实是缺夹具。
- **清理测试数据之后必须重跑 setup** ✓，否则验收会出现同样假象。
- 对话矩阵 setup 需要 `APIGX_REAL_UPSTREAM_KEY`（真实上游 key **只从环境变量读** ✓，不写进仓库 ✓）。
- 视频脚本依赖 `.toolchain/_state/video-task.json`（由 setup 生成 ✓）。
- 报"回归"之前先读**具体报错**：本例 503 直接指出缺渠道 ✓，不必先怀疑代码 ✓。
## 八、在 PowerShell 里执行 Node 片段（本会话踩了三次的坑）

**约定**：需要跑 Node 代码（打补丁、批量改文件）时，**一律用 `write` 工具把脚本写成 `.mjs` 文件再 `node` 执行**；
不要在 PowerShell 里用 `node -e "..."` 内联，更不要在双引号字符串里再嵌双引号。

**为什么（实测代价）**：
- PowerShell 会**先解析整条命令**：任何引号错误 ⇒ **整段脚本一个字都不执行**。本会话有一次我据此以为补丁已生效，
  实际没有 —— 差点得出错误结论。
- 内联脚本里的 `\"` 转义、模板字面量的 `${}`、正则里的 `[^\W]`，都会被 PowerShell 先吃掉一层；
  补丁脚本越复杂，写对的概率越低。
- 写成文件后，内容由 Node 直接解释，转义 / 编码（UTF-8）/ 多行字符串都不再歧义。

**配套约定**：
1. 补丁脚本**必须自校验**：改完读回文件核对关键片段，校验失败就 `exit 1`，绝不"改了就算"；
2. 锚点优先选**不含缩进的短子串**（缩进会被 gofmt/prettier 改动，整段替换极易失配）；
3. 补丁脚本放 `.toolchain/_state/` 下，执行完删除；
4. 纯文本追加（如本文档）可以用 PowerShell **单引号 here-string**（`@'...'@`）安全完成。
