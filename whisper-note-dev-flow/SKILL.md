# 轻记 · 项目开发流程管理

本 skill 管理项目的长期可维护性，包括项目文档、任务清单、代码风格、codebase-memory-mcp 代码库记忆和 git 规范。

所有文档文件都在本 skill 文件夹内：
- `PROJECT_STATUS.md` — 项目长期文档（读写，序号倒序，顶部最新）
- `TASK_LOG.md` — 任务清单（只追加，顶部最新，完成后打勾）
- `CODE_STYLE.md` — 代码风格规范（Google 为主 + 项目补充）

## 触发机制

### 0. 每轮对话开始时（强制前置，不可跳过）

**适用场景**：每条用户消息到达后，只要该消息涉及本项目（代码改动、编译错误、调试、状态查询、任务规划、子任务完成、任务完成等），**必须先调用本 skill**，再处理具体任务。

**严禁的反模式**：
- ❌ 看到编译错误就直接 Read/Edit 修复（跳过 skill）
- ❌ 看到调试需求就直接读代码（跳过 skill）
- ❌ 中间过程认为"任务还没完成"就不调 skill

**正确流程**：
```
用户消息到达
  ↓
[强制] 内心扫描 skills 列表，判断是否涉及本项目
  ↓ 涉及
[强制] 调用 whisper-note-dev-flow skill
  ↓
在 skill 内部判断本轮消息属于哪类：
  - 任务规划     → 走 §3
  - 任务执行     → 走 §3.5（中间过程）
  - 子任务完成   → 走 §7（部分更新）
  - 任务完成     → 走 §4 + §6
  - 状态查询     → 走 §2
  ↓
执行对应流程
```

**为什么必须强制前置**：
- 中间过程（编译错误修复、调试）也会改动项目文件，需要 skill 同步文档/任务清单
- 跳过 skill 会导致 PROJECT_STATUS.md / TASK_LOG.md 与实际进度脱节
- 避免注意力被具体问题占据而忘记流程

### 1. 新对话开始时（自动，§0 的特例）

静默执行以下步骤，不打断用户：

**Step 1：读取项目文档**
```
读取 .trae/skills/whisper-note-dev-flow/PROJECT_STATUS.md
读取 .trae/skills/whisper-note-dev-flow/TASK_LOG.md
```

**Step 2：读取 codebase-memory-mcp（可用时）**

1. 调用 `list_projects`，按当前仓库根目录和项目名称确认对应索引，禁止凭名称猜测。
2. 已索引时调用 `index_status`。仅当本轮需要理解架构或定位上次核心模块时，再调用一次 `get_architecture(aspects=["overview"])` 或 `search_graph`。
3. 尚未索引时，仅在当前仓库位于 `CBM_ALLOWED_ROOT` 允许范围内时调用一次 `index_repository(repo_path=<仓库根目录>, mode="fast")`；不在允许范围或 MCP 不可用时跳过，并在其影响本轮判断时简短说明。
4. 只有确实需要追踪调用关系时才调用 `trace_path`；需要评估当前改动影响时才调用 `detect_changes`。

codebase-memory-mcp 用于快速定位结构和影响范围，源代码仍是最终事实。启动阶段通常最多调用 2 次查询工具，避免无目标扫描；不得回退到其他知识图谱工具建立第二套索引。

**Step 3：风险提醒**

检查 PROJECT_STATUS.md 中的 ⚠️ 不稳定项数量和 TASK_LOG.md 中未完成待办数量：
- ⚠️ 不稳定项 > 3 个 → 主动提醒用户优先处理
- 未完成待办 > 10 个 → 提醒用户考虑拆分或清理

提醒格式：
```
⚠️ 项目风险提醒：
- 不稳定项 X 个（阈值 3）：[列出]
- 未完成待办 Y 个（阈值 10）
建议优先处理不稳定项再开始新任务。
```

### 2. 用户要求读取时

用户说"读取项目状态" / "看看项目进度"等 → 重新执行 Step 1 + Step 2，并向用户汇报当前状态摘要。

### 3. 任务规划时（写入）

用户描述新任务后，在开始执行前写入 TASK_LOG.md：

```markdown
## [进行中] <任务名称> (<日期>)

**本轮目标**：<一句话描述>
**验收标准**：<可验证的标准>

**预计涉及模块**：
| 模块 | 文件 | 类型 | 说明 |
|---|---|---|---|
| <模块名> | <文件路径> | 新建/修改/移植 | <说明> |
| ... | ... | ... | ... |

**任务清单**：
- [ ] <子任务1>
- [ ] <子任务2>
- [ ] <子任务3>
```

追加到 TASK_LOG.md **顶部**（在 `# 任务清单` 标题之后）。

### 3.5 任务执行中（中间过程，不新增序号）

**适用场景**：编译错误修复、调试、子任务实现过程中。

**要求**：
- 不新增 PROJECT_STATUS.md 序号（避免文档膨胀）
- 不改 TASK_LOG.md 的 `[进行中]`/`[已完成]` 状态
- 但**每次代码改动后必须告知用户当前子任务进度**（如"编译验证 [ ]→[x]"）
- 如发现新的代码约定，追加到 CODE_STYLE.md（见 §5）
- 仅当某子任务**通过验证**（如编译通过、测试通过）时，按 §7 部分更新 TASK_LOG.md

### 4. 任务完成时（写入）

任务完成并验证通过后，更新两个文档：

**更新 PROJECT_STATUS.md**（顶部追加，序号递增）：

```markdown
### [<序号: 3位数字>] <日期> <任务名称>

**做了什么**：<一句话描述>

**涉及模块**：<模块1、模块2、模块3...>

**改动明细**：
| 文件 | 模块 | 改动说明 |
|---|---|---|
| <文件路径> | <模块名> | <具体改动描述> |
| ... | ... | ... |

**验证**：<cargo check ✅ / npm build ✅ / 测试结果 / 零警告等>
**剩余风险**：<列出新引入的风险或已解决的风险，无则写"无">
```

同时更新 PROJECT_STATUS.md 顶部的「当前阶段」和「当前任务」区块。

**更新 TASK_LOG.md**：
- 将 `[进行中]` 改为 `[已完成]`
- 所有 `- [ ]` 改为 `- [x]`
- 每个任务后追加改动文件（如 `- [x] 搭建项目结构 → harmony/`）

### 5. CODE_STYLE.md 自动更新

以下情况追加 CODE_STYLE.md：
- 开发中发现新的代码约定（如某 API 的特殊用法）
- 某个模式反复出现需要统一（如错误处理方式）
- FFI 封装、状态管理等项目特有约定

每 5 轮任务结束时整理一次（去重、分类、排序），但不删除已有内容。

### 6. 任务完成后推荐下一轮

更新文档后，分析以下信息：
1. PROJECT_STATUS.md 中的路线图和剩余风险
2. TASK_LOG.md 中的未完成待办
3. ⚠️ 标记的不稳定项

推荐 2-3 个下一步选项，用 `AskUserQuestion` 让用户选择：
- 选项 1（推荐）：路线图中的下一阶段
- 选项 2：处理 ⚠️ 不稳定项
- 选项 3：其他待办

用户选择后自动写入 TASK_LOG.md 开始下一轮；用户也可选"其他"自定义。

### 7. 子任务完成时（部分更新，不新增序号）

**适用场景**：TASK_LOG.md 当前 `[进行中]` 任务中某个 `[ ]` 子任务**通过验证**（如编译通过、单模块测试通过、签名配置完成），但整个任务尚未全部完成。

**操作**：
- 将该子任务 `- [ ]` 改为 `- [x]`，并追加改动文件/验证结果
- **不新增** PROJECT_STATUS.md 序号
- **不改** TASK_LOG.md 的 `[进行中]` 状态
- 简短告知用户当前进度（如"5/8 子任务完成"）
- 不调用 git commit（避免半成品 commit，等整个任务完成再提交）

**示例**：
```markdown
- [x] 编译验证（用户在 DevEco Studio 中 Build > Build Hap(s)，反馈错误） → 修复 12 个 ArkTS 编译错误，BUILD SUCCESS
```

### 8. 每轮对话完成时（强制收尾，不可跳过）

**适用场景**：每轮对话即将结束（AI 准备输出最终回复前），只要本轮消息涉及本项目，**必须再次调用本 skill 做收尾检查**。

**严禁的反模式**：
- ❌ 直接输出最终回复而不做收尾检查
- ❌ 认为只是回答问题/闲聊就跳过收尾（只要涉及本项目就必须收尾）
- ❌ 收尾检查发现要补更新，但偷懒不补
- ❌ 只在"任务完成"时收尾，"中间过程"不收尾

**正确流程**：
```
本轮任务处理完毕，准备输出最终回复
  ↓
[强制] 调用 whisper-note-dev-flow skill 做收尾检查
  ↓
收尾检查清单：
  1. 本轮是否有代码/文档改动？
     - 是 → 确认 PROJECT_STATUS.md / TASK_LOG.md 已同步（按 §3.5/§4/§7）
     - 否 → 跳过
  2. 是否有子任务通过验证？
     - 是 → 按 §7 在 TASK_LOG.md 打勾
     - 否 → 跳过
  3. 是否整任务完成？
     - 是 → 按 §4 全量更新 + git commit + 检查 codebase-memory-mcp 索引状态 + §6 推荐下一步
     - 否 → 跳过
  4. 是否发现新的代码约定？
     - 是 → 追加 CODE_STYLE.md（按 §5）
     - 否 → 跳过
  5. 给用户简短进度确认
     - 格式："本轮已完成 X，剩余 Y；当前任务进度 M/N"
  ↓
输出最终回复
```

**为什么必须强制收尾**：
- 避免文档与实际进度脱节（开始时调 skill 但结束时忘记同步）
- 给用户明确的进度反馈，不让用户自己猜
- 捕获"中间过程"中遗漏的文档更新
- 形成"开始 → 执行 → 收尾"的完整闭环

**与 §0 的关系**：
- §0 是"开始时强制前置"——确保进入正确流程
- §8 是"结束时强制收尾"——确保文档同步、进度反馈
- 两者配合，形成完整闭环；缺一不可

## Git 管理规范

### Commit 规范

格式：`<type>: <description>`

type 可选：
- `feat`: 新功能
- `fix`: 修复
- `refactor`: 重构
- `docs`: 文档
- `chore`: 构建/依赖

示例：
```
feat: 鸿蒙端 Core Speech Kit 语音识别封装
fix: 录音 use-after-free（显式 drop stream 后清标志）
docs: 更新 PROJECT_STATUS.md [004]
```

### Commit 时机

每轮任务完成并验证通过后 commit 一次。不要在任务中途 commit 半成品。

### 禁止提交

- 构建产物（target/, dist/, build/, .hap）
- 依赖目录（node_modules/, .hvigor/）
- 敏感文件（.env, 密钥, local.properties）
- IDE 配置（.vscode/, .idea/）
- `.codebase-memory/` 本地索引与缓存（只有用户明确要求共享持久化索引时才提交指定产物）

### Commit 后自动操作

```
1. git commit 完成
2. 调用 `index_status(project=<项目名>)` 确认 codebase-memory-mcp 索引状态
3. 索引缺失或过期时，在允许根目录内调用 `index_repository(repo_path=<仓库根目录>, mode="fast")`
4. 需要给出改动影响面时，再调用 `detect_changes(project=<项目名>, scope="impact")`
```

如果 codebase-memory-mcp 不可用或仓库不在 `CBM_ALLOWED_ROOT` 内，跳过索引步骤并说明原因；不要安装替代图谱工具或扩大允许根目录。

## codebase-memory-mcp 集成

### 项目与索引

- 先用 `list_projects` 解析当前仓库对应的项目名，再把该项目名传给其他工具。
- 用 `index_status` 检查现有索引；缺失或过期时才调用 `index_repository`。
- 默认使用 `mode="fast"`。只有任务明确需要语义相似度或更完整的跨文件关系时才使用 `moderate`/`full`。
- `persistence` 默认关闭；只有用户明确要求团队共享索引产物时才开启。

### 按需查询

- `get_architecture(aspects=["overview"])`：快速了解模块边界，适合新任务或状态梳理。
- `search_graph`：按符号、关键词或文件范围定位实现，找到候选后必须直接读取相关源代码。
- `trace_path`：追踪调用链或数据流，仅在调用关系是当前问题关键时使用。
- `detect_changes(scope="impact")`：查看当前变更的调用方影响面，服务于改动验收。
- `query_graph`：只有常规查询无法回答问题时使用；先读取 `get_graph_schema`，再写受限的 Cypher 查询。

### 使用边界

- codebase-memory-mcp 是导航和影响分析工具，不替代源代码、编译结果和测试证据。
- 尊重 `CBM_ALLOWED_ROOT`；不得为了完成普通任务擅自扩大允许目录。
- 不自动调用 `delete_project`、`manage_adr`、`ingest_traces` 等与当前任务无关或会改变外部状态的工具。
- 不建立或维护第二套代码索引。

## 跨端共享代码（shared/）

当项目有跨端逻辑共享需求时，在项目根目录建立 `shared/` 目录：

```
shared/
├── nlp-parser.ts      # 纯逻辑，无平台依赖
├── llm-engine.ts      # 纯 fetch，三端通用
└── note.ts            # 数据模型
```

- **Windows**：直接 import 引用
- **鸿蒙**：hvigor 引用或构建时复制
- **Android**：人工同步 Kotlin 版本（逻辑一致）

修改 shared/ 代码需同步验证所有引用端。

## 注意事项

1. **静默读取**：新对话开始时读取文档应静默进行，不要输出大段文档内容给用户，只在需要时引用
2. **序号递增**：PROJECT_STATUS.md 的序号从 001 开始，每次 +1，3 位数字
3. **顶部最新**：两个文档都是顶部为最新内容，新内容追加在标题之后
4. **读写而非只写**：PROJECT_STATUS.md 建议读写，即执行任务前也要读取了解上下文
5. **诚实记录**：验证失败要如实记录，剩余风险不可隐瞒
6. **不删除历史**：两个文档都不删除历史记录，只追加
7. **强制前置（§0）**：任何涉及本项目的用户消息都必须先调用 skill，严禁跳过 skill 直接编辑代码/文档。中间过程（编译错误、调试）也属于此范畴
8. **部分更新（§7）**：子任务完成时只打勾，不新增 PROJECT_STATUS.md 序号，不 commit；只有整任务完成时才走 §4 全量更新 + commit
9. **强制收尾（§8）**：每轮对话结束前必须再次调用 skill 做收尾检查，确认文档已同步、进度已反馈。与 §0 强制前置配合，形成"开始 → 执行 → 收尾"完整闭环；缺一不可
